# 掲示板（docs/board/）の運用

このリポジトリの `docs/board/` を、関係するセッションどうしの連絡に使う。口頭（チャット）で決めたことも、ここに書いたものだけを正とする。

## 役割

| 名前 | 誰か | 主にすること |
|---|---|---|
| 本線 | 手元の Windows で動く Claude Code | GPU を使う作業、統合、判断点。main への取り込み |
| 支線 | クラウドの Claude Code セッション（複数可） | GPU を使わない部品。担当の枝で作業し、PR で返す |
| 監督 | Cowork の Claude（共同研究者） | 報告の点検、判断、指示書の作成 |
| 決裁 | 指導側（人） | 承認。最終判断 |

## 置き場所と名前

```
docs/board/
  README.md            この文書
  STATUS.md            いま誰が何をしているかの一覧（本線が更新）
  NNNN_<差出>_<種類>_<題>.md
```

- NNNN：通し番号（4桁）。main に直接書く人（本線・決裁の書き写し）が、既存の最大番号＋1を使う
- **支線の枝の中では、仮の番号 `cNN`（例 `c01_cloud-runner_report_….md`）を使う。** 本線が取り込むときに正式な番号（NNNN）を振り、ファイル名と「番号」の行を直し、対応表を STATUS.md に残す（2026-09-25、決裁の指示。掲示板 0027）
  - 枝の中での参照は `c01` のように書く。取り込み後も本文の `cNN` はそのまま残し、対応表で引く
  - 監督の指示書や回答を支線が保存するときも `cNN` を使う
- 差出：`main`（本線）、`cloud-<枝名>`（支線）、`review`（監督）、`human`（決裁）
- 種類：`report`（報告）、`ask`（判断を求める）、`order`（指示）、`answer`（回答）、`review`（点検結果）
- 例：`0007_cloud-expert_report_注入の調整.md`、`0008_review_answer_0007への判断.md`

## 1通の書き方

```markdown
# <題>
- 番号: NNNN / 差出: <差出> / 宛先: <宛先> / 日時: YYYY-MM-DD HH:MM（日本時間）
- 返信先: <番号。なければ「なし」>
- 状態: 未読 | 対応中 | 完了 | 取り下げ
- 関係する枝・PR・コミット: <あれば>

## 要点（3行以内）

## 本文
（事実、数字、完了条件の結果。判断を求めるときは選択肢と、それぞれの後戻りのしやすさ）

## 求めること
（ask のときは、何を決めてほしいか。order のときは、完了条件）
```

## 決まり

1. 書いたら、その場でコミットして push する。書き込みは掲示板の新しいファイルだけにし、既存の文書は書き換えない。訂正するときは新しい番号で出す（STATUS.md だけは本線が上書きしてよい）
2. 判断待ち（ask）を出したら、その件は答えが来るまで先へ進めない（手順書の段階制と同じ）
3. 支線は `main` に直接 push しない。担当の枝で作業し、PR にする。取り込むのは本線
4. 秘密：リポジトリ（fujikro0814-del/VLAcompetition）は**公開**。共同作業者を追加しない。鍵、個人の情報、学内の回線の設定（プロキシのアドレス・証明書）、C:\VLA の記録・データ・卒研の資料を、掲示板にもリポジトリにも置かない（流用したコードと場面の定義は可）。push の前に毎回ステージを検査する（0002、0004）
5. 数字は必ず出所（コマンド、出力ファイル、コミット）と一緒に書く
6. 迷ったら仮定で埋めず、ask を出して止まる
