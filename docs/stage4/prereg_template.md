# 事前登録の雛形（段階 4。docs/目標書_段階4.md 第 6 節の手順）

使い方:
- 事前登録 v1（テスト 1）、v2（テスト 2、束 4 が残った場合だけ）など、回す前に 1 通ずつこの雛形をコピーして埋める。コピー先は `docs/stage4/prereg_v1.md` のように新しいファイルにする（この雛形は書き換えない）。
- 【記入】の所を埋める。【固定】は決まりの文書で決まっているので変えない。【結果を見た後】は、事前登録の時点では書かず、決める人と決め方だけを書く。
- 埋め終わったら、コミット → SHA-256 を掲示 → 新しい帯で一度だけ回す。回した後に、主要評価項目・基準・帯・分母を書き換えない。
- 読むもの: `docs/目標書_段階4.md`、`configs/s4_gates.json`。書くもの: この雛形のコピーだけ。

## 6. 非劣性の余裕の書き方（RTC などで非劣性を主張するとき）

RTC の主張を「naive に劣らない」と書く場合は、次の 4 つを**回す前に**書く。1 つでも書けないなら、非劣性を主張せず、仕組みの指標で述べて、成功率は信頼区間で記述するだけにする（critique #5）。

1. **余裕の幅 Δ:** 【記入】例: −10 ポイント。
2. **向き:** 「対象の成功率 − naive の成功率 > −Δ」を示す。片側。【記入】
3. **信頼区間の方法:** 【記入】例: 対のデータに対する Newcombe（対あり）の 95% 区間。下限が −Δ より上なら非劣性。
4. **検出力の確認:** 試行数 198 対で、同じ強さの設定でも示せる確率を書く。critique #5 の計算（c3_ni_and_budget.json）では次のとおり。

   | 余裕 | 198 対で非劣性が示せる確率（naive と同じ強さの設定） |
   |---|---|
   | −5 ポイント | 26〜37% |
   | −10 ポイント | 76〜90% |

   この表の確率は、食い違い率 0.19〜0.28（30 s・旧ドライバの前例）から出したもの。事前登録では、物差し K の d0（30 s の採点、新ドライバ）で計算し直した値を並べる。【記入】

   余裕 −5 ポイントでは、仕組み上ほぼ示せない。「確認では通り、テストでは非劣性を示せない」が最も起きやすい結果なので、この表を事前登録に写す。

- 余裕の幅は、結果を見る前に決める。結果を見た後に広げることはしない。【固定】
- 余裕を何にするか（−5 か −10 か、仕組みの指標だけにするか）は作者の判断（D2）。【記入】

仕組みの指標で述べる場合の指標【固定】: 最初に閉じた位置の半径方向の差、移動の比、継ぎ目の速度の跳び、躍度（Wilcoxon 検定）。「70〜85/99」のような見込みの数字は看板にしない。

## 7. 解析の手順

1. 集計は**独立な 2 つの実装**で行う。一致は、件数が完全一致、中央値が ±0.5 mm 以内。不一致なら、原因を直すまで報告しない。【固定】
2. 検定:
   - 成功の対（同じ種）: McNemar の正確検定（両側）。
   - 層別: 種で層別した正確検定（H2）。
   - 区間: Wilson（単一の割合）、Newcombe（差）。
   - 躍度などの連続量: Wilcoxon の符号順位検定。
   - 【記入】他に使うもの。
3. 補正: 主要評価項目の族に Holm。【固定】
4. 分母の書き方: 「分母は〜」を表の脇に必ず書く（誘発が成立した試行、対で両方成立した種、など）。【固定】
5. 報告の順: 事前登録の主要評価項目から順に、起きたとおりに。副次は「副次」と明記。事前登録にない解析は「事後の解析」と明記する。【固定】
6. 物差し K の d0（30 s の採点が主、60 s の採点が副）を、全報告の脇に載せる。小さな差は成功率ではなく仕組みの指標で述べる。【固定】
7. 段階 3 の数字と並べるときは、「段階 3（旧ドライバ 560.94、30 s）」と脇に書き、段階 4（新ドライバ 610.88）との差にはドライバの差（と、段階 4 は試行ごとに世界を作り直すこと）が入って分けられないことを書く。段階 3 と比べるのは 30 s の採点（主。同じ定義）で行う。E7 は段階 3 と同じ 1 手順 30 s・全体 200 s で回すので、そのまま並べる。【固定】
8. 出力: `outputs/s4/` と `outputs/v2eval/S4*/` だけ。出力のハッシュを掲示する。【固定】

## 8. 事前に決めた停止の条件

回している途中でも、次のどれかに当たったら、その場で止めて掲示板に出し、規則どおりに処理する。【記入】で足してよいが、回した後に足さない。

| 条件 | 処理 |
|---|---|
| 監査 G1〜G3 に違反が 1 件でも出た | 止める。原因を直す。直した後の再開は、落ちた試行を同じ種で回し直すだけ。違反が出た試行は除外せず、報告する |
| `verify-s3` の不一致が出た（凍結したファイルの変更） | 止める。凍結ファイルを元に戻す。報告する |
| メモリ不足・プロセスの異常終了 | 落ちた試行を退避し（消さない）、同じ種で回し直す。件数と理由を報告する。再開は人が行う |
| 夜間の再起動・シャットダウン | 同上。サインインの後に `96_s4_ops.py wait`／`progress.json` で止まった所を見て、`96_s4_resume.py` で続きから回す（切れた試行は `_incomplete_*` に退避して同じ種で回し直す） |
| GPU ドライバ・OS の版が実行の途中で変わった | 止める。変わった後の試行を別の環境として分け、掲示板に出す。どちらの環境の試行も消さずに報告する |
| E7 の試行全体の上限（200 s）が効いた | 止めない。件数を数え、逸脱の節に書く |
| API の失敗 | 同じ種で 1 回だけ回し直す。件数を報告する |
| 新しい種のモデルが崩れた | H2 に含めて報告する。止めない |
| 締め（10/19 24:00）に間に合わない | 間に合わなかった構成は、提出物には「進行中」と 1 行だけ書き、研究の道に回す。同じ関門を使う |
| 【記入】この事前登録に固有のもの | 【記入】 |
