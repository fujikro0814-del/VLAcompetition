## 1. 目的

3 個の連続タスク（「全部片付けて」→ 色の順の手順 → 方策が 1 色ずつ箱へ運ぶ）で、手順が決められた時間（1 手順の試み 30 s x 2 回）で終わらなかったとき、今の実行器は止まって人に知らせるだけである。段階 3 では 20 回中 6 回が成功し、止まった 16 回のうち 12 回は 2 番目の手順で止まった。

U4 は、その止まる所で、失敗の記録と知覚の要約を LLM に渡して次の手を選ばせ、利用者向けの日本語の状況報告を書かせる。問いは 2 つ:

1. 立て直しの計画を挟むと、3 個とも収まる試行・平均の収納数・人への知らせ（止まり）の数は、同じ種の今の実行器と比べてどう変わるか（記述）。
2. LLM の日本語の状況報告は、真値と照らしてどれだけ正しいか（記述）。

### 2-1 立て直しの手と弾く規則（`replan_s4.py` の冒頭と同じ。回す前に固定）

| 手 | 意味 | 通す条件 |
|---|---|---|
| next | 次の色を 1 つ選ぶ（失敗した色をもう 1 度でもよい）。残りは元の順 | 色が「残りの候補」にある |
| reorder | 残りの色の順を付け直す（例: 失敗した色を後に回す） | 並びが「残りの候補」の並べ替え（全部・重複なし） |
| skip | 失敗した色を飛ばし、残りで続ける | 色が失敗した色 |
| finish | 箱にある色を報告して終える | いつでも |
| stop | 止まって人に知らせる（今の実行器と同じ） | いつでも |

- 残りの候補: 今の計画で成功も飛ばしもしていない色のうち、知覚で机の上に見えていて（seen・held）、箱の中になく、手の中・見失いでなく、同じ色の手順が 2 回に達していないもの。
- 弾く: 応答が読めない、手が 5 つ以外、机の上にない色、箱の中の色、同じ色の 3 回目以上、重複、並べ替えになっていない並び、失敗した色でない色の skip。弾いたら安全な手 **stop**（今の実行器と同じ止まり方と同じ文）に倒し、弾いた理由を記録する。
- 立て直しが 2 回に達した後の失敗は、LLM を呼ばずに今の実行器と同じに止まる。
- next・reorder を通したのに、これから実行する色の並びが空になったとき（規則を通れば起きない。守りとして）は、`empty_order` として記録し、stop に倒す。

**注: 「同じ色の 3 回目以上」の数え方（作者の判断: 案 A で回す。2026-10-08 20:05 ごろ）**

1 つの手順の中で、方策は最大 2 回試す（試み 30 s x 2。やり直し 1 回）。「回」を何で数えるかで、方策がその色に使える試みの数が変わる。

| 案 | 数えるもの | 上限 | その色に使える試み | 実装 |
|---|---|---|---|---|
| A（既定・今の実装） | 同じ色の**手順**の数（飛ばした手順は数えない） | 2 手順まで | 最大 4 回（2 手順 x 2 回） | `replan_s4.runs_of`・`MAX_RUNS_PER_COLOR = 2` |
| B | 同じ色の**試み**の数（`steps[].attempts` の合計） | 例: 3 回まで | 最大 3 回（立て直しの後の手順は 1 回目で打ち切りになりうる） | 未実装（選ぶなら `runs_of` を試みの和に替え、上限の値を決めて版を上げる） |

案 A は、立て直しの後の手順を今の実行器と同じ形（やり直し 1 回つき）で回せるが、1 色に最大 4 回・約 120 s を使い、全体 200 s の打ち切りに近づく。案 B は時間を抑えられるが、手順の途中で上限に達したときの扱い（やり直しを打ち切るか）を実行器に足す必要がある。作者は案 A を選んだ（10/08）。
- 報告の検査: 空でない・2 文以内・90 字以内・日本語を含む・`scripts/60_paper.py` の FORBIDDEN の語（モデルの記号を含む）と英語の色の名前・方策や LLM の名を含まない。落ちたら手はそのまま使い、報告だけ記録と知覚から決まる定型の文に替える（`report_source` = template）。
- 続ける手（next・reorder・skip）のときは、やり直しの前と同じ「待機位置へ戻す動き」の後に次の手順を始める。stop のときは戻さずにその場で止まる（今の実行器と同じ）。

### 2-2 実行系が見るもの（G1）

立て直しの計画役に渡すのは、指示文・計画の色の列・実行器自身の記録（手順ごとの結果と試みの回数）・知覚の WorldModel の色の状態（机の上・箱の中・手の中・見失い）だけ。シミュレーションの真値は使わない。`executor_u4.py` は runtime の入れ物の中にあり、`scripts/check_g1_boundary.py` の厳しい検査（違反 0）と、試行ごとの到達検査（`task_loop` の `g1_audit`）を受ける。真値（`truth_success_t`・`final_in_box`）は、終わった後の採点（第 5 節）だけに使う。

## 5. 日本語の報告の採点の規則（回す前に固定）

対象: U4 の各立て直しの報告（`replans[].report`。弾いて倒した stop の定型の文を含む）。`summary` の `reports` の表に、報告・そのときの知覚の箱の中（`perceived_box`）・依頼の時刻までに真値で箱に収まった色（`truth_box_at_request`）・通した手（`action`・`applied`）を並べる。

報告の中の主張を 3 種類に分けて、それぞれ正・誤・言及なしを付ける:

1. **終わらなかった色**: 報告が名指しした「入れられなかった色」が、失敗した手順の色と同じで、かつ真値でその時刻に箱に収まっていなければ正。真値で既に収まっていた（判定の取りこぼし）なら誤（知覚・判定の誤りに由来、と別に数える）。
2. **箱の中の色**: 報告が箱の中の色を述べたとき、述べた色の集まりが `truth_box_at_request` と一致すれば正。「何も入っていない」は真値が空のときだけ正。述べていなければ言及なし。
3. **次にすること**: 報告が述べた次の動き（どの色を先に・飛ばす・終える・止まる）が、実際に通した手（`action`・`applied.order`）と一致すれば正。述べていなければ言及なし。

- 報告が正しい: 1 が正で、2・3 に誤がない。
- 1 に言及がない報告は「正しくない」に数える（何が起きたかを伝えるのが報告の役目）。
- 採点は、記録を見られる 2 人（作者と、別の担当または別のセッション）が独立に付け、食い違いは上の規則に戻って決める。食い違いの数も出す。
- LLM の文（`report_source` = llm）と定型の文（template）を分けて正しさを出す。
- 表記の検査（2 文以内・FORBIDDEN の語なし）は実行時に機械で済んでいる。採点では内容だけを見る。

## 6. 評価中に API を呼ぶことと再現性

- 評価の間、起動時の計画役と立て直しの計画役が Anthropic の API を呼ぶ。claude-haiku-5-5 は温度を受けないので、キャッシュに無い入力の答えは呼ぶたびに変わりうる。そのため U4 の試行は、同じ種でも回し直すと同じにならない（方策の GPU の揺らぎとは別の、もう 1 つの揺らぎ）。
- 扱い:
  1. 応答は鍵（モデル・送らない温度・thinking・SYSTEM・SCHEMA・入力・PROMPT_VERSION・種類）ごとに `outputs/llm_cache/<鍵>.json` に残す。読めた応答だけを残す。同じ入力が来たら残した応答を使う（同じ入力の答えはキャッシュで保証）。
  2. 試行の json の `replans[].out.llm` に、呼び出しの数・キャッシュから読んだか・応答のモデル名・`stop_reason`・`request_id`・トークン・失敗の理由を残す。弾いた応答も `llm_output` に残す。
  3. 回し終えたら `outputs/llm_cache/` の一覧と SHA-256 を記録とともに保管する（集計は記録だけから再現できる）。
  4. 報告には、キャッシュから読んだ立て直しの数と、新しく呼んだ数を書く。応答のモデル名が途中で変わったら、変わった所で分けて報告する。
  5. U4S の立て直しは `replan_multi` の鍵（種類 `replan_multi`・モデル・送る設定を含む）で同じ `outputs/llm_cache/` に残す。U4 の鍵とも、立て直しの試験台（`outputs/s4/replan_bench/cache/`）の答えとも混ざらない。claude-sonnet-5-5 も温度を受けないので、扱いは 1〜4 と同じ。
- API の失敗: 立て直しは同じ入力で 1 回だけ回し直し、それでも駄目なら stop に倒す（その試行は「LLM の失敗で倒した」に数える）。起動時の計画役の API の例外は、D-E7 と同じく同じ種で試行を 1 回だけ回し直し、2 回目も失敗したら止める（続きから回すと同じ種で回る）。鍵が無いときは U4 を回さない（入口が止める）。

## 7. 全体 200 s の打ち切り（回す前に決めた扱い）

- 目標書 第 3-1 節 2 と同じ扱いにする。全体 200 s の打ち切りが効いた試行（記録の `timed_out`）の**件数を条件ごとに報告**し、**1 件でも効いたら、事前登録の逸脱として第 11 節に書く**（試行の番号・種・`t_end` を並べる。`summary` の `deviations_timed_out`）。
- 打ち切られた試行も分母から外さない。3 個とも・収納数は、打ち切りの時点の真値（終わりの `final_in_box`）で数える。
- U4 は立て直しの分（LLM の待ち・待機位置へ戻す動き・やり直しの手順）だけ時間を使うので、U0 より打ち切りが増えうる。その差も並べる。

## 13. 既知の限界

- 立て直しの計画役は画像を見ない。知覚の要約（色の状態）と実行器の記録だけで決める。知覚が箱の中の色を取りこぼすと、計画と報告の両方が誤りうる（第 5 節の 1 で別に数える）。
- 続ける手のときは待機位置へ戻すので、手に立方体を持ったまま失敗した場合は戻す動きで指を開く（やり直しの前の戻す動きと同じ）。そのときの立方体の行き先は記録の真値でしか分からない。
- 全体 200 s の打ち切りは変えない。立て直した試行は時間が足りずに打ち切られうる（打ち切りの数を出す）。
- 100 本 x 3 条件（U4S を足せば 4 条件）の記述だけで、差の有無は主張しない。
- U4S を足すかは、段階 3 の 16 の止まった場面（5 回ずつ）だけで決める。場面の数が少ないので、規則を満たしても U4S が U4 より良いとは言えない（試験台は記述だけ）。
