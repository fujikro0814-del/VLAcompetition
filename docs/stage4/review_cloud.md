### 軽微 4. SHA-256 の照合が、取り出したときの改行に依存する
- **場所**: scripts/96_s4_resume.py:80・106-110。掲示板 0154 と計画の script_sha256。
- **何が起きるか**
  - SHA82（e36e12…）は LF の blob の値である。この clone は core.autocrlf=true で、取り出したファイルは fff62b… になるので、96 は起動を拒む（安全側に倒れる）。逃げ道の `--allow-82-change` を使うと照合が全部無効になる。
  - 0154・計画の SHA も、CRLF の clone で照合すると偽の不一致になる（下請けが 6 ファイルで確かめた）。
  - 照合は「82 が変わっていない」ことだけを守る。写しの中身が 82 と同じかは守らない。私が手で比べた範囲では、文書に書かれた違い（計画役・制限時間・世界の作り直し・記録に足した欄）以外は同じだった。
- **直し方の案**: CRLF を LF に正規化してから計算する（または `git hash-object`）。`.gitattributes` に `*.py text eol=lf` を置く。写しと 82 の関数を AST で比べる検査を足す。
- **確かめ方**: 動かした（この PC で両方の値を計算した）。

## この包みで数十時間の評価を始めてよいか

**はい（条件つき）。**

理由:
- 包み（96_s4_resume.py）は、試行の記録を壊したり、壊れた記録を完全とみなしたりする道を持たない。合成の破損はすべて「不完全」と判定され、完全な記録は上書きも削除もされない。
- 制限時間・環境の食い違いでは止まる。
- 82 の写しは、文書に書かれた違い以外は同じだった。
- 診断の指標の関数も、掲示した定義どおりだった。

ただし、次を守ることを条件にする。重要 1〜7 の多くは、包みの外側（解析・監視・台帳・束の外側の包み）が、不完全な状態を「済み」「問題なし」として通してしまう道である。

1. 束の実行中は、作業場所のコードを更新しない（重要 4）。
2. 束が終わったら、解析の前に、全条件で次を確かめる。
   - run.json と G_AUDIT（met=true）がある
   - 本数・種の集合が計画どおり
   - env_segments が 1 つ
   - git_head と各 SHA がそろっている
   - 欠けていれば、該当の 96 を呼び直す（重要 1・3）
3. 夜通しの監視では、wait の「完了待ち」だけに頼らない。progress の current_started と経過時間を人が見るか、時間切れを付ける（重要 6）。
4. 台帳の照合は、出力の parse_errors が 0 であることも確かめる（重要 5）。
5. E7 の時間ごとの曲線の定義（重要 2）と、30.0 s の境界（軽微 1）は、結果を見る前に決めて掲示する。
6. 束 3（学習）を評価と重ねるときは、99 の点検に頼らず、評価が 1 本以下であることと物理の空き 12 GB を人が確かめる（重要 8）。

上の 2・4・5 を満たせない場合、その条件の結果は報告に使わない。
